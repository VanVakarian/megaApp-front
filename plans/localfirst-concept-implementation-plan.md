# Local-first concept implementation plan

## Цель

Создать приложение, в котором все операции с данными сначала выполняются локально (localStorage), а затем синхронизируются с сервером.
Обеспечить мгновенный отклик для пользователя, актуальность данных между устройствами, и обработку ошибок без поддержки полноценного оффлайн-режима.

## Основные принципы

1. **Local-first**
   Все CRUD-операции сначала выполняются локально.
   UI моментально обновляется.

2. **Фоновая синхронизация**
   После локальных изменений данные отправляются на сервер через очередь.
   Если сервер не отвечает в течение заданного времени (например, 5 секунд), изменения откатываются, пользователю показывается ошибка.

3. **Получение актуальных данных**
   При запуске приложения сначала отображаются данные из localStorage.
   Параллельно отправляется запрос на сервер для проверки актуальности.
   При получении новых данных из сервера (через SSE) localStorage и UI обновляются.

4. **Мониторинг сети**
   Приложение отслеживает состояние сети.
   Если соединения нет, пользователь блокируется от изменений и получает уведомление.

5. **Межустройствовая синхронизация**
   Если приложение открыто на нескольких устройствах, изменения с одного устройства быстро распространяются на другие через SSE.

6. **Обработка ошибок**
   В случае сетевых проблем, задержек или ошибок синхронизации — откат изменений и информирование пользователя.
   При отсутствии сети изменения блокируются до восстановления соединения.

7. **Конфликты**
   Сценарии с одновременным редактированием игнорируются.
   Оффлайн-режим не поддерживается, все изменения должны быть подтверждены сервером.
   При невозможности синхронизации — откат и блокировка изменений.

## АНАЛИЗ ТЕКУЩЕЙ АРХИТЕКТУРЫ СИСТЕМЫ ЕДЫ

### 🏗️ КОМПОНЕНТЫ И СТРУКТУРА

**FoodService (основной сервис)**
- Центральная точка управления всеми данными о еде
- Содержит WritableSignal'ы для реактивного состояния:
  - `diary$$` - сырые данные дневника питания
  - `diaryFormatted$$` - форматированные данные с вычисленными калориями и процентами
  - `selectedDayIso$$` - выбранная дата
  - `catalogue$$` - каталог продуктов
  - `catalogueMyIds$$` - ID продуктов пользователя
  - `coefficients$$` - коэффициенты для продуктов
- Вычисляемые сигналы:
  - `catalogueSortedListSelected$$` - отсортированные выбранные продукты
  - `catalogueSortedListLeftOut$$` - отсортированные невыбранные продукты

**Автоматическая подгрузка данных (умная пагинация)**
- Система автоматически подгружает данные при приближении к границам загруженного диапазона
- `loadedRange$$` - отслеживает загруженный диапазон дат
- `shouldLoadMore()` - проверяет нужна ли подгрузка (порог 3 дня до границы)
- `loadMoreData()` - выполняет асинхронную подгрузку через `getFoodDiaryFullUpdateRange()`
- Триггер через effect: при изменении `selectedDayIso$$()` автоматически проверяется нужность подгрузки

**Компоненты UI**
1. **FoodDiaryComponent** - основной компонент дневника
   - Отображает список записей за день
   - Управляет аккордеонами для редактирования
   - Вычисляет процент съеденных калорий и отображение прогресса

2. **DiaryEntryNewFormComponent** - форма добавления новой записи
   - Автокомплит для выбора продукта
   - Валидация веса и продукта
   - Расчет проекции процента съеденных калорий в реальном времени
   - Создание записи с историей действий

3. **DiaryEntryEditFormComponent** - форма редактирования записи
   - Два режима изменения веса: абсолютный и относительный
   - История изменений записи
   - Удаление записи
   - Проекция изменений в реальном времени

**Операции CRUD (текущая реализация)**
1. **Создание записи** (`createDiaryEntry`)
   - POST к `/api/food/diary/`
   - При успехе обновляет локальное состояние через `updateDiaryEntryWithNewValues`
   - Автоматически получает ID с сервера

2. **Редактирование записи** (`editDiaryEntry`)
   - PUT к `/api/food/diary`
   - При успехе обновляет локальное состояние
   - Добавляет новую запись в историю изменений

3. **Удаление записи** (`deleteDiaryEntry`)
   - DELETE к `/api/food/diary/${id}`
   - При успехе удаляет из локального состояния через `removeDiaryEntry`

4. **Чтение данных** (`getFoodDiaryFullUpdateRange`)
   - GET к `/api/food/diary-full-update`
   - Параметры: дата и offset для диапазона
   - Мерджит полученные данные с существующими

**Система каталога продуктов**
- Создание новых продуктов: `createNewCatalogueEntry`
- Редактирование продуктов: `editCatalogueEntry`
- Управление персональным каталогом: `pickUserFoodId`, `dismissUserFoodId`
- Коэффициенты продуктов для персонализированных калорий

**FoodStatsService**
- Отслеживает статистику по дням
- Обновляется при изменениях в дневнике
- Вычисляет графики весов и калорий

### 🔍 КЛЮЧЕВЫЕ ОСОБЕННОСТИ ТЕКУЩЕЙ АРХИТЕКТУРЫ

**Реактивная система**
- Все компоненты подписаны на сигналы FoodService
- Автоматическое обновление UI при изменении данных
- Вычисляемые поля (калории, проценты) обновляются реактивно

**Сложные вычисления**
- Форматированные записи дневника включают:
  - Калории с учетом коэффициентов продукта
  - Процент от дневной нормы
  - Статус прогресса для UI
- Группировка данных по датам с агрегацией

**Умная загрузка данных**
- Предзагрузка данных вокруг выбранной даты
- Автоматическая подгрузка при приближении к границам
- Мерджинг новых данных с существующими

**Интеграция с другими системами**
- FoodStatsService для статистики
- SettingsService для пользовательских настроек
- Система авторизации и персонализации

### 🚨 СЛОЖНОСТИ МИГРАЦИИ НА LOCAL-FIRST

**1. Сложная структура данных**
- Многоуровневая вложенность: Diary[date].food[id]
- Зависимости между каталогом, коэффициентами и записями
- Необходимость синхронизации связанных данных

**2. Вычисляемые поля**
- Калории рассчитываются на основе веса, каталога и коэффициентов
- При изменении одного элемента нужно пересчитывать связанные
- Сложность отката при ошибках синхронизации

**3. Автоматическая пагинация**
- Система подгружает данные автоматически
- Нужно различать локальные и серверные данные
- Конфликты при одновременной подгрузке и local-first операциях

**4. История изменений**
- Каждая запись содержит массив истории действий
- При откате нужно корректно обработать историю
- Возможны конфликты при параллельных изменениях

**5. Межсвязанные операции**
- Изменение записи влияет на статистику дня и общую статистику
- Создание нового продукта влияет на каталог
- Сложность атомарности операций
