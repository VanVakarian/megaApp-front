# Food Action Feedback Notifications — Implementation Plan

## Goal

Довести черновой `NotificationService` до релизного состояния и подключить его к реальному UI, начиная с food-модуля: пользователь должен видеть честный статус каждого write-действия (добавление/правка/удаление записи дневника, удаление и восстановление дня, вес тела) — мгновенный optimistic-результат, затем (если нужно) промежуточное «сохраняю...», и только в конце либо зелёное подтверждение, либо красную ошибку, если все попытки сервера провалились. Money/транзакции — следующая фаза, после того как паттерн обкатан и выглядит хорошо на еде.

## How It Works Now

- `src/app/services/notification.service.ts`
  - signal `notifications$$` + методы `showSyncError/showSyncSuccess/showOfflineMode/showSyncInProgress/showNetworkError`
  - каждое уведомление живёт ровно 5000ms, без возможности обновить/заменить существующее
  - `clearAll()` приватный и не используется
  - **нет ни одного компонента, который рендерит `notifications$$`** — сервис полностью не подключен к UI
  - реально вызывается только из `settings.service.ts` (`showSyncError` при ошибке сохранения настроек) и `network.service.ts` (`showOfflineMode` при потере соединения)
- `src/app/services/sync-queue.service.ts`
  - один глобальный singleton FIFO на всё приложение (food, money, settings, auth — общая очередь)
  - `addOperation()` принимает `successCallback`/`rollbackCallback`, но не отдаёт наружу никакого промежуточного статуса («пытаюсь», «N-я попытка»)
  - retry: до `BACKGROUND_SYNC_RETRIES_MAX` (3) попыток, пауза `1000 * retryCount` мс между попытками, таймаут одной попытки `BACKGROUND_SYNC_TIMEOUT_MS` (8000мс) — итого до ~30 секунд от первой попытки до финального провала
  - при исчерпании попыток: `rollbackCallback()`, операция выкидывается из очереди, и **`break` выходит из всего `while`-цикла** — если за провалившейся операцией в очереди стояли другие (от любого домена), они замораживаются и не обработаются, пока кто-то не вызовет `addOperation()` снова и не перезапустит `processQueue()`
- `src/app/services/food/food-base.service.ts`
  - тонкая обёртка: `addSyncOperation()` просто прокидывает вызов в `SyncQueueService.addOperation()`, никакой доменной логики уведомлений
- `src/app/services/food/food-diary.service.ts` — все write-методы (`createDiaryEntry`, `editDiaryEntry`, `deleteDiaryEntry`, `deleteSelectedDayEntries`, `restoreSelectedDayEntries`, `setUserBodyWeight`) следуют одному паттерну:
  1. синхронная проверка `checkNetworkAvailability()` — если сети нет, `console.error` + `return false`/`{result:false}`, **никакого сигнала пользователю**
  2. optimistic update локального state + localStorage + stats — мгновенно, без сети
  3. `addSyncOperation()` с `rollbackCallback` (откатывает optimistic state), у `createDiaryEntry`/`restoreSelectedDayEntries` есть ещё `successCallback` (подменяет tempId на реальный id с сервера)
  4. метод возвращает `true`/`{result:true}` сразу после шага 3, **не дожидаясь реального ответа сервера**
- `src/app/services/food/food-catalogue.service.ts` — `saveProduct()`/`deleteProduct()` устроены принципиально иначе: прямой `HttpClient` запрос (без sync-queue), ошибка пробрасывается как `Promise` rejection
- Компоненты:
  - `diary-entry-add-form.ts` — `submitForm()` блокирует форму, ждёт `createDiaryEntry()`, при успехе закрывает модал; **при ошибке ничего не происходит**, форма просто разблокируется
  - `diary-entry-edit-form.ts` — `onSubmit()`/`deleteDiaryEntry()` оборачивают вызов в `try/catch`, но `editDiaryEntry`/`deleteDiaryEntry` никогда не бросают исключение (см. выше) — `catch` мёртвый код
  - `food-diary.ts` — `onDeleteDayConfirmed()`/`onRestoreDayClicked()` просто `await`-ят результат, вообще не проверяя его
  - `body-weight.ts` — единственное место, где есть хоть какой-то error-feedback: вручную `throw new Error()`, если `setUserBodyWeight()` вернул `false`, и показывает `VInputAutoSubmitResult.Error` на 1мс через `VInputAutoSubmitManager`. Но `setUserBodyWeight()` возвращает `false` только при отсутствии сети в момент вызова — реальный провал сервера (после исчерпания retry, который случится на несколько секунд позже) этим механизмом не перехватывается вообще
  - `catalogue-entry-edit-form.ts` — единственный компонент с приличным UX: `isSaving$$`/`isDeleting$$` спиннеры + `error$$` сигнал с текстом ошибки в форме. Но при успехе нет вообще никакого позитивного подтверждения — форма просто закрывается
- `src/app/services/network.service.ts` — `isOnline$$`/`isNetworkAvailable$$` (один и тот же сигнал), при переходе в offline сразу глобально показывает `showOfflineMode()` через `NotificationService` (хотя сам `NotificationService` всё равно никуда не рендерится)
- `src/app/services/auth.interceptor.ts` — все ошибки, кроме 401 с возможностью refresh, пробрасываются дальше как есть, не глушатся

## Why The Current Bugs Happen

- Пользователь не видит вообще никаких toast/уведомлений, потому что для `NotificationService` никогда не был написан UI-компонент — сервис существует только как data layer в воздухе
- Diary-флоу (create/edit/delete/delete-day/restore-day/body-weight) **никогда не сигнализирует о финальной ошибке наружу** — вызывающий компонент получает `true` сразу после optimistic update и больше не имеет связи с тем, что произойдёт через 1–30 секунд в sync-queue. К моменту реального провала форма/модал уже почти наверняка закрыты — значит локальный feedback в принципе не может сработать, нужен глобальный канал
- Catalogue-флоу устроен по другому контракту (throw + try/catch), поэтому компонент дневника, написанный «по аналогии», ловит `catch`, который никогда не выстрелит — мёртвый код, создающий ложное чувство, что ошибки обрабатываются
- `body-weight.ts` единственный, кто пытался добавить feedback, но завязался на синхронный early-return вместо реального результата фоновой синхронизации — то есть тоже не покрывает настоящий сценарий «сервер ответил ошибкой после retry»
- `SyncQueueService` не даёт точки расширения для промежуточного статуса («жду ответа», «повторная попытка») — есть только начало (`addOperation`) и два конца (`successCallback`/`rollbackCallback`), поэтому сценарий «прошла 1 секунда, а ответа всё ещё нет» физически не из чего собрать без изменения самого sync-queue
- Баг с `break` в `processQueue()` означает, что если когда-нибудь очередь застрянет на проигравшей операции с операциями позади неё, эти операции не доедут до сервера, пока пользователь не совершит новое действие где угодно в приложении — то есть даже если мы добавим красивые уведомления, под капотом могут оставаться зависшие операции

## Decisions To Freeze Before Implementation

- Где живёт оркестрация pending/success/error?
  - В `SyncQueueService` — он уже единственное место, которое знает тайминг попыток, retry-count и финальный исход. Никакого отдельного «feedback-сервиса» не вводим (лишний слой)
  - `SyncOperation`/`addOperation()` получают новое опциональное поле `feedback: { successMessage, errorMessage, pendingMessage? }` — если поле не передано, поведение операции не меняется (money/settings/auth продолжают работать как раньше без всплытия toast)
  - заодно обработку одной операции (весь её цикл retry) выносим из общего `while`-цикла `processQueue()` в отдельную внутреннюю функцию, обрабатывающую ровно одну операцию от начала до её success/financial fail. Внешний цикл очереди просто последовательно await-ит эту функцию по одной операции и переходит к следующей **независимо от исхода** — это одновременно убирает баг с `break` (не нужен ни `break`, ни `continue`, очередь физически не может зависнуть) и даёт естественное изолированное место для хранения pending-state на время жизни одной операции
- Какая схема состояний для одной операции?
  - `t=0` (enqueue): optimistic update уже применён локально и видим пользователю — никакого toast пока не нужно
  - Чисто time-based триггер, без доп. условий: если за **1000мс** (финальное значение; в первой итерации было 2000мс, сократили после ручной проверки в браузере — 2с ощущались как слишком долгое ожидание) с момента enqueue операция не получила финального исхода (ни success, ни financial fail) — показать **жёлтый** (`warning`) pending-toast («Сохраняю...»)
  - pending-toast **не имеет авто-скрытия вообще** — висит до тех пор, пока операция не получит success или financial fail. Это единственный тип toast в системе без таймера
  - Если ответ (success или financial fail) приходит раньше 1000мс — pending-toast никогда не появляется, таймер просто гасится, сразу зелёный/красный toast
  - Финальный успех → если pending-toast уже показан — удалить именно его по id и добавить новый success-toast; если не показан — просто добавить success-toast. Авто-скрытие через 5с
  - Финальный провал (после исчерпания всех retry, после rollback) → если pending-toast уже показан — удалить его по id и добавить error-toast. Авто-скрытие тоже через 5с (единая длительность для success/error — отдельные константы 2.5с/7с из первой итерации убрали как избыточные, раз оба свелись к одному числу)
  - Таймер pending привязан к моменту `enqueue`, а не к моменту реальной отправки HTTP-запроса — если операция стоит в очереди за другой долгой операцией (очередь общая, single-flight), пользователь всё равно должен увидеть «жду ответа», это честно отражает его ожидание. Это осознанно даёт возможность увидеть **несколько параллельных жёлтых toast одновременно**, если пользователь успел запустить несколько действий подряд — ожидаемое и нормальное поведение, не корнер-кейс для исключения
  - **Важный фикс после первой реализации**: таймер изначально был запланирован внутри per-operation функции, которая стартует только когда очередь реально берёт операцию в обработку — а не в момент enqueue. Из-за single-flight очереди вторая операция, стоящая за первой, могла вообще не получить свой pending-toast, пока не закончится первая (поймано вручным тестированием: два последовательных редактирования, второе уведомление не появлялось). Исправлено переносом планирования таймера в `addOperation()` — состояние (`pendingTimeoutId`/`pendingNotificationId`) хранится прямо на объекте операции, а не в локальной переменной внутри обработчика
- Как хранится state pending-toast на время ожидания — нужна ли отдельная id→operation структура?
  - Не нужна. id текущего pending-toast (если он показан) хранится как поле на самом объекте операции (`pendingNotificationId`), живёт ровно столько, сколько живёт операция в очереди/обработке, и не видно снаружи `SyncQueueService`
  - Рассматривался вариант «просто `clearAll()` при любом success/fail» — отклонён: при параллельных операциях он погасит чужие toast (в т.ч. чужие pending от других ещё не завершённых действий), что и есть тот самый корнер-кейс, который хотелось избежать. Точечное удаление по id — не сложнее в реализации (один `removeNotification(id)` вызов) и не имеет этого побочного эффекта, поэтому выбран он
  - Со стороны `NotificationService` это требует только: `addNotification()` возвращает id и принимает флаг «не авто-скрывать», `removeNotification()` становится публичным. Никакого «update/patch по id» API не нужно — снаружи это всегда «удалить старый toast по id, добавить новый», а не «изменить существующий на месте»
- Управляются ли toast «снаружи» (из вызывающего кода), и как?
  - Да — но единственный внешний управляющий код для pending/success/error в food-флоу — это `SyncQueueService` (через `feedback` на операции), не сами компоненты. Компоненты/сервисы верхнего уровня (catalogue quick win, ранний no-network отказ) используют `NotificationService` напрямую только для разовых неуправляемых toast (add → авто-скрытие), без необходимости держать id у себя
- Что делать с синхронным early-exit «нет сети» (до optimistic update, до sync-queue)?
  - Сейчас в этом случае: optimistic update не применяется вообще (запись не появляется), `console.error`, и компонент тихо ничего не делает. Глобальный `showOfflineMode()` от `NetworkService` в этот момент тоже может быть уже скрыт/неактуален и вообще говорит про другое (намекает, что изменения сами засинкаются позже — а тут они вообще не были поставлены в очередь)
  - Решение: каждый такой ранний выход в `food-diary.service.ts` должен сам вызвать явное немедленное уведомление об ошибке именно для этого действия («Нет соединения — запись не сохранена»), а не полагаться на общий offline-banner
- Нужно ли распространять то же самое на `food-catalogue.service.ts` (`saveProduct`/`deleteProduct`)?
  - Нет, не трогаем механику. Там уже нормальный синхронный try/catch с конкретным текстом ошибки внутри формы — отдельный (правильный) паттерн для модалки с активной кнопкой submit, его ломать не нужно
  - Но добавляем туда **только** позитивный success-toast (сейчас после успешного сохранения/удаления продукта нет вообще никакого подтверждения, кроме закрытия модалки) — мелкое, безопасное дополнение поверх существующего error-handling
- Нужно ли чинить `break` в `SyncQueueService.processQueue()`?
  - Да, обязательно, независимо от уведомлений — иначе после первого окончательно провалившегося action любые другие очередью операции (включая money/settings/auth) могут зависнуть в очереди до случайного следующего вызова `addOperation()`. Заменяем `break` на `continue`, чтобы цикл продолжал обрабатывать остаток очереди после провала одной операции
- UI для toast — новый ui-kit компонент или расширение существующего?
  - Новый presentational `v-toast` в `src/ui-kit/components/v-toast/` (иконка/спиннер, текст) по аналогии с остальными `v-*` компонентами (свой `.ts/.html/.css/readme.md`)
  - Закрытие — **не выделенный крестик**, а клик/тап в любую точку карточки (`(click)` на host-элементе, `cursor: pointer`). Крестик оставлен в компоненте как опция (`isCloseButtonVisible`, default `false`) для будущих flow, но ни один текущий вызов его не включает
  - Новый app-level host `src/app/components/notifications/notifications.ts` — подписывается на `NotificationService.notifications$$`, рендерит стек `v-toast`, монтируется один раз в `app.component.html` (как `<navigation />`), не зависит от роута
  - Позиция: **низ-лево** (после ручной проверки в браузере поменяли с исходного верх-право на низ-лево по прямому запросу) — низ-право занят FAB-меню навигации (`z-50` в `navigation.html`), низ-лево свободен. Toast-слой должен быть выше навигации и **выше открытых модалок** — ошибка о провале фоновой операции не должна потеряться, даже если в этот момент открыт другой модал
  - Цвет — не только иконка, а тонированный фон + цветная рамка через `color-mix(in oklch, var(--v-color-success/warning/danger/primary) 14%, var(--v-color-surface) 86%)` — чистая иконка на белом фоне оказалась недостаточно заметной при ручной проверке
- Нужно ли пользователю давать кнопку «повторить» в error-toast?
  - Нет, не в этой итерации. Optimistic state уже откатился (запись пропала / вес вернулся к старому значению) — это само по себе понятный сигнал «надо повторить действие руками». Кнопка retry — возможное будущее улучшение, не блокирует релиз

## How It Should Work

### Создание записи дневника (`diary-entry-add-form.ts` → `createDiaryEntry`)
- Запись мгновенно появляется в дневнике (как сейчас, optimistic)
- Модалка закрывается как сейчас при `result === true`
- Дальше уже не важно, открыта форма или нет — глобальный toast сам доведёт историю до конца:
  - быстрый успех (<1с) → сразу зелёный «Запись добавлена», без промежуточного шага
  - дольше 1с без ответа → жёлтый «Сохраняю...» (висит до исхода) → меняется на зелёный/красный
  - нет сети в момент клика → красный «Нет соединения — запись не сохранена» сразу, без optimistic-добавления (как сейчас)

### Правка записи (`diary-entry-edit-form.ts` → `editDiaryEntry`)
- Тот же паттерн. Дополнительно: `try/catch` в компоненте теряет смысл (исключение никогда не прилетит) — убираем мёртвый `catch`, форма просто включается после получения булева ответа, а судьбу запроса досказывает toast

### Удаление одной записи (`diary-entry-edit-form.ts` → `deleteDiaryEntry`)
- Тот же паттерн, что и правка

### Удаление всех записей за день / восстановление дня (`food-diary.ts` → `deleteSelectedDayEntries` / `restoreSelectedDayEntries`)
- Те же 3 состояния. Текст уведомлений — про день целиком («Записи за день удалены» / «Не удалось удалить записи за день» и аналогично для восстановления)

### Вес тела (`body-weight.ts` → `setUserBodyWeight`)
- Сохраняем существующий мгновенный inline-flash на самом инпуте (`VInputAutoSubmitResult`) для быстрого тактильного отклика — он не мешает
- Но реальным источником правды для отложенного результата становится глобальный toast: если save проходит не сразу — pending-toast, итоговый результат — success/error toast, независимо от того, ушёл ли пользователь с экрана веса

### Каталог продуктов (`catalogue-entry-edit-form.ts` → `saveProduct` / `deleteProduct`)
- Error-handling не трогаем (уже хорош)
- Добавляем success-toast при успешном сохранении/удалении — единственное изменение здесь

## Required Changes

### `src/app/services/sync-queue.service.ts`
- вынести обработку одной операции (попытка → retry → success/rollback) из общего `while` в `processQueue()` в отдельную функцию на одну операцию; внешний цикл очереди просто await-ит её по одной операции за раз и идёт дальше независимо от исхода — `break`/`continue` больше не нужны, очередь не может зависнуть
- расширить `SyncOperation`/`addOperation()` опциональным `feedback: { successMessage: string; errorMessage: string; pendingMessage?: string }`
- состояние pending-toast (`pendingTimeoutId`, `pendingNotificationId`) — поля прямо на объекте операции, не локальная переменная внутри per-operation функции (важно: см. фикс в Decisions/Step 8 — таймер планируется в `addOperation()`, в момент enqueue, а не внутри per-operation функции, иначе он не запустится, пока очередь не освободится)
- в `addOperation()`, при наличии `feedback`:
  - запланировать таймер `NOTIFICATION_PENDING_DELAY_MS` (1000мс); по истечении, если операция ещё не разрешена — `addNotification('warning', pendingMessage, { persistent: true })`, id записать в `operation.pendingNotificationId`
- в per-operation функции:
  - при success — погасить таймер; если `pendingNotificationId` не null — `removeNotification(pendingNotificationId)`; затем `addNotification('success', successMessage)` (автоскрытие, `NOTIFICATION_DEFAULT_DURATION_MS` = 5000мс)
  - при financial fail (после исчерпания retry, после `rollbackCallback`) — погасить таймер; если `pendingNotificationId` не null — `removeNotification(pendingNotificationId)`; затем `addNotification('error', errorMessage)` (та же длительность, 5000мс — отдельная error-константа из первой итерации убрана)

### `src/app/services/notification.service.ts`

## Minimal Acceptance Criteria

- Любое write-действие в food-модуле (create/edit/delete записи, delete/restore дня, вес тела) заканчивается видимым пользователю зелёным или красным итогом, независимо от того, остался ли он на том же экране
- Промежуточное жёлтое «Сохраняю...» показывается только когда реально нужно (задержка >1с без финального исхода), а не на каждое действие, и не имеет автоскрытия — висит до success/error
- Несколько параллельных действий показывают несколько независимых pending-тостов, не блокируя друг друга по времени появления
- Провал одной операции в sync-queue не останавливает обработку остальной очереди
- Отказ из-за отсутствия сети до постановки в очередь — явный и честный, не маскируется общим offline-banner
- Старые toast не переживают logout/смену пользователя
- Catalogue-флоу (продукты) получает позитивное подтверждение успеха, не теряя существующий error-handling
- Закрытие toast — тапом по карточке, без обязательного крестика

## Code Review

Самостоятельный разбор всего диффа после ручного тестирования пользователем.

### Найдено и исправлено
- **Pending-toast не появлялся у второй операции, пока не завершится первая** (Critical, найдено пользователем при ручной проверке с отладочной задержкой). Причина: таймер планировался внутри per-operation функции, которая стартует только когда очередь реально берёт операцию в работу — а очередь single-flight, поэтому вторая операция могла подолгу ждать своей очереди, не успев даже запланировать свой таймер. Исправлено переносом планирования в `addOperation()` (см. Step 8) — таймер стартует строго в момент постановки в очередь, состояние живёт на самом объекте операции (`pendingTimeoutId`/`pendingNotificationId`), а не в локальной переменной обработчика.
- **Двойной `onClose.emit()` при клике на крестик** (Minor, спящий баг — крестик пока нигде не включён). Поскольку весь host `v-toast` теперь сам слушает `(click)`, клик по кнопке-крестику внутри бабблился и вызывал `close()` дважды. Исправлено: `onCloseButtonClick()` делает `event.stopPropagation()` перед вызовом `close()`.
- **Неиспользуемое поле `protected readonly Icon = IconName`** в `v-toast.ts` — мёртвый код, шаблон обращается к `icon$$()` напрямую. Удалено.

### Рассмотрено и не считается багом
- `v-toast` кликабельна целиком (`(click)` на host), но без `role="button"`/`tabindex`/keydown-обработчика — не доступна с клавиатуры. Это осознанно не блокирующая находка: ровно тот же паттерн (clickable host без keyboard-поддержки) уже используется в `v-card` (`onCardclick`) до этой задачи — не регрессия, а существующая конвенция кодовой базы. Стоит когда-нибудь поднять отдельно для всех clickable-карточек сразу, не только для toast.
- Отладочная задержка в `sync-queue.service.ts` (`createRequest()`, блок `// DEBUG:`) оставлена в файле в закомментированном виде по просьбе пользователя — пока удобно для будущих ручных проверок, не влияет на прод-поведение, пока закомментирована.
