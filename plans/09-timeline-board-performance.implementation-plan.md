# Timeline Board Performance — Implementation Plan (Frontend)

Продолжение работы над `timeline-board` (экран Time, полотно). Уже сделано ранее (не в скоупе этого плана): windowed rendering по дням (рендерится только видимое окно строк + буфер вместо всех загруженных дней), singleton-тултип на ховере вместо `v-tooltip`-компонента на каждый сегмент, фикс вечно растущего z-index в `ZLayerService`.

После этих фиксов лёгкий джиттеринг остался — особенно при скролле, и даже когда полотно не двигается вообще (например при открытии формы редактирования категории в соседней колонке того же экрана). Ниже — 4 независимые находки по итогам анализа, каждая фиксится отдельно.

## Находка 1 — `background-attachment: fixed` на дашед-линиях сетки

`timeline-board.scss`: `.timeline-grid-line` (23 шт., статичный оверлей поверх `timeline-scroll`, сам не скроллится) и `.seg-grid-line` (несколько штук на **каждый видимый сегмент**, `segmentGridLines()`) используют `background-attachment: fixed` + `repeating-linear-gradient`. Это один из самых дорогих CSS-приёмов: браузер не может закомпозить такой фон на GPU-слое, вынужден перерисовывать его на main thread при скролле и часто — при любом repaint страницы вообще (например при появлении оверлея модалки где угодно на экране).

- `.timeline-grid-line` — сам элемент не скроллится (лежит вне `.timeline-scroll`), `fixed` для него функционально бесполезен (эффекта на визуал не даёт, ставился по инерции/копипасте). Убрать без риска.
- `.seg-grid-line` — здесь `fixed` был осознанным приёмом: сегмент скроллится вместе со строкой дня, а его дашед-линия должна визуально совпадать по фазе с фоновой `.timeline-grid-line` (см. комментарий в `timeline-board.html` про "white on top of the segment"). Без `fixed` фаза дашей на сегменте будет отсчитываться от собственного верха `.seg`, а не от вьюпорта — **лёгкое визуальное расхождение с фоновой сеткой возможно** (даши на сегменте и даши на фоне позади него разъедутся на несколько пикселей). Решение: убрать `fixed` и здесь — альтернатива (пересчитывать `background-position` на каждый скролл-тик через JS) сама по себе создаёт новую нагрузку и противоречит цели задачи. Если визуально будет мешать — откатить точечно одной строкой.

## Находка 2 — производные данные сегмента не мемоизированы

`segmentsFor()`, `segmentLabel()`, `segmentColor()`, `segmentBackground()`, `segmentGridLines()` вызываются как обычные методы в шаблоне (`timeline-board.html`), не через `computed()`. `OnPush` решает **когда** компонент попадёт на перепроверку, но не экономит саму работу внутри уже попавшего на неё шаблона — при любом dirty-check компонента Angular заново вызывает все эти методы для всех видимых сегментов.

`pickerState$$`/`hoveredSegment$$`/`previewSlot$$` — сигналы, которыми владеет сам `TimelineBoard`. Открытие пикера (клик "создать запись") пишет `pickerState$$` → это помечает dirty весь компонент → Angular пересчитывает **все** сегменты во всех видимых строках заново, хотя по факту изменилось только состояние пикера.

Решение — развести на два слоя:
- **Базовый computed** (`segmentsBaseByDayTrack$$`) — строит готовые сегменты (label, color, tooltip-friendly clock/duration, grid-lines) из `entriesByDay$$()` + каталожных сигналов (`activityKindById$$`, `optionById$$`, `areaGroupId$$`). Зависит **только** от них — не от `activeAdjustment$$`, не от `pickerState$$`, не от `hoveredSegment$$`. Пересчитывается только когда реально меняются записи или справочник активностей/категорий.
- **`activeAdjustment$$` (жив-драг) остаётся вне этого computed намеренно** — он меняется на каждый `pointermove` во время драга; если завязать на него весь базовый computed, при драге будет пересчитываться база для всех дней на каждый пиксель вместо одного. Сборка "база + оверлей текущего драга" остаётся дешёвым методом (`segmentsFor`), но теперь просто достаёт готовый массив из `Map` за O(1) и подмешивает максимум один сегмент — вместо пересчёта label/color/gridlines с нуля.
- Итог: локальные изменения состояния компонента (пикер, тултип, previewSlot) больше не трогают дорогую часть вообще; драг остаётся дешёвым как и был (не регрессирует).

## Находка 3 — `onLaneMouseMove`/`findGapSlot` сканируют весь датасет на каждый пиксель мыши

`findGapSlot()` фильтрует **весь** `entries$$()` (все загруженные дни истории) на каждое событие `mousemove` внутри лейна, плюс `onLaneMouseMove` делает `getBoundingClientRect()` (синхронный layout-read) на каждый вызов. При скролле трекпадом курсор часто остаётся над той же лейной — mousemove и скролл дублируют нагрузку одновременно.

- Скоуп по дню через уже существующий индекс `entriesByDay$$()` — свой день + предыдущий (единственные два дня, чьи записи вообще могут пересекать сегодняшний диапазон минут: запись следующего дня физически не может начинаться раньше `dayAbsBase + 1440`, значит на "разрыв" сегодня повлиять не может — тот же инвариант, на котором уже стоит `segmentsFor`) — вместо плоского перебора всех записей. Итог — O(десяток записей за 2 дня) вместо O(всей истории).
- Дедуп перед записью сигнала: `previewSlot$$.set(...)` сейчас пишет новый объект на каждый tick мыши, даже если по факту слот не изменился (объект — всегда новая ссылка, значит для сигнала это всегда "новое значение" → dirty-check всего компонента). Добавить сравнение с текущим значением перед записью — не писать, если слот идентичен предыдущему.

## Находка 4 — zone.js: высокочастотные события гоняют change detection на каждый тик

Проект на `provideZoneChangeDetection()` (`main.ts`), не zoneless. Zone.js патчит все `addEventListener` — это касается как `(scroll)` в шаблоне, так и сырых `document.addEventListener('pointermove', ...)` в `startMove`/`startResize` (драг/ресайз сегмента). Каждое такое событие триггерит `ApplicationRef.tick()` — полный обход дерева приложения от корня.

- **Скролл**: вместо Angular-байндинга `(scroll)` — нативный listener, навешанный на `timelineScrollElem` вручную (там же, где уже вешается `ResizeObserver`), с `{ passive: true }`, зарегистрированный через `ngZone.runOutsideAngular(...)`. Внутри — throttling через `requestAnimationFrame` (не чаще кадра), вход в зону (`ngZone.run(...)`) — только на итоговую запись `scrollTop$$` и уже существующую проверку "не пора ли подгрузить более старые дни".
- **Драг/ресайз** (`startMove`/`startResize`): регистрация `document.addEventListener('pointermove', ...)` — под `ngZone.runOutsideAngular`, запись `activeAdjustment$$` — тоже через rAF-коалесинг (визуально 60 апдейтов/сек более чем достаточно для плавного драга, живее человеческий глаз всё равно не различит). `pointerup` — единичное редкое событие, без throttling, но вызов оборачивается в явный `ngZone.run(...)`, чтобы итоговый коммит (`updateEntryTime`/открытие пикера) сразу попал в change detection.
- `onLaneMouseMove` остаётся в шаблонном байндинге (внутри зоны) — здесь высокочастотность уже закрывается находкой 3 (дешевле стало само вычисление + дедуп перед записью сигнала), выносить из зоны отдельной директивой на каждый лейн — заметно больше сложности за небольшой дополнительный выигрыш, не в этой итерации.

## Находка 5 (обнаружена постфактум, при живой проверке) — вспышка/скачок при подгрузке более старых дней сверху

При скролле вверх до триггера `prependOlderDays` — на несколько кадров мигает пустотой/чужим содержимым и весь список ощутимо дёргается, прежде чем снова плавно продолжить скроллиться.

Причина — рассинхрон между виртуализацией (появилась в более раннем этапе этой же работы) и анкорингом скролла (более старый код, не рассчитанный на виртуализацию): `prependOlderDays` синхронно растит `visibleStartDayNumber$$` (→ `days$$()` длиннее), но `scrollTop$$` (сигнал, управляющий окном виртуализации через `visibleRowRange$$`) обновляется только когда естественным образом долетит нативное `scroll`-событие после того, как `afterNextRender` физически переставит `scrollEl.scrollTop` — то есть на кадр (и то не сразу, а после — rAF-коалесинг из находки 4 добавляет ещё один кадр задержки поверх). На это время Angular считает окно виртуализации по старому `scrollTop$$`, но уже по новому (выросшему) числу дней — окно временно "смотрит" не туда.

Фикс — использовать уже существующий инвариант "высота строки фиксированная и известная" (`rowHeightPx$$()`): компенсация скролла на 30 новых дней считается аналитически (`scrollTop$$() + OLDER_DAYS_BATCH * rowHeightPx$$()`), без ожидания измерения `scrollHeight` после рендера. `scrollTop$$` обновляется синхронно, в тот же тик, что и `visibleStartDayNumber$$` — первый же последующий рендер уже видит согласованную пару (новое число дней + новый scrollTop), без промежуточного неверного кадра. `afterNextRender` остаётся — но только чтобы физически переставить реальный `scrollEl.scrollTop` под уже корректно отрисованное состояние, а не чтобы его "подгонять" постфактум.
