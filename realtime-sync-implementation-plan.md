### 🚀 Real-time Sync (WebSocket): Концепт и План Внедрения [Frontend]

#### Цель
Интегрировать в Angular-приложение WebSocket-клиент, который будет устанавливать соединение с сервером, слушать события об изменениях данных и инициировать обновление локального состояния (`Signals`), чтобы UI автоматически и мгновенно отражал изменения, сделанные на других устройствах.

#### Концепция и Архитектура
Система будет построена на четком разделении ответственности между сервисами, что соответствует вашему текущему стилю.

1.  **`NetworkService` (Менеджер Соединения)**
    *   Единственный сервис, который "знает" о существовании WebSocket. Он инкапсулирует всю низкоуровневую логику.
    *   Будет использовать `rxjs/webSocket` для создания надежного и управляемого соединения.
    *   **Важно:** Авторизация происходит на этапе установки соединения через query-параметр `token` и `clientId` в URL: `ws://server/api/ws?token=${token}&clientId=${clientId}`
    *   Генерирует уникальный `clientId` при инициализации (например, `crypto.randomUUID()`) для идентификации текущей сессии.
    *   Реализует методы `connect()` и `disconnect()` с логикой автоматического переподключения.
    *   Предоставляет единый `Observable` (`getMessages()`) для всех входящих сообщений с сервера.
    *   Реализует heartbeat/ping-pong механизм для поддержания соединения.

2.  **`AuthService` (Управляющий Жизненным Циклом)**
    *   Отвечает за то, *когда* нужно устанавливать и разрывать соединение.
    *   Вызывает `networkService.connect()` после успешного логина пользователя и при проверке аутентификации (`checkAuth`).
    *   Вызывает `networkService.disconnect()` при выходе пользователя из системы (`logout`).

3.  **Доменные Сервисы (`FoodDiaryService`, `FoodStatsService` и т.д.)**
    *   Являются "потребителями" данных.
    *   Подписываются на `Observable` сообщений из `NetworkService`.
    *   Фильтруют сообщения по `type`, чтобы реагировать только на те, что относятся к их домену.
    *   **Ключевой момент:** Получив уведомление, сервис **не будет пытаться вручную изменить локальное состояние**. Вместо этого он вызовет свой собственный метод для запроса актуальных данных с сервера. Это гарантирует консистентность данных и повторно использует уже существующую логику.

4.  **Интеграция с HTTP-запросами**
    *   Все HTTP-запросы должны включать заголовок `X-Client-ID` со значением `clientId` из `NetworkService`.
    *   Это позволяет серверу исключать инициатора изменений из рассылки уведомлений, предотвращая дублирование обновлений.

#### План Внедрения

#### Типы WebSocket-сообщений от сервера
Согласно серверной реализации, клиент будет получать следующие типы сообщений:

**Дневник питания:**
- `DIARY_ENTRY_CREATED` - payload: `{ id, dateISO }`
- `DIARY_ENTRY_UPDATED` - payload: `{ id, dateISO }`
- `DIARY_ENTRY_DELETED` - payload: `{ id }`

**Вес тела:**
- `BODY_WEIGHT_CREATED` - payload: `{ dateISO, weight }`
- `BODY_WEIGHT_UPDATED` - payload: `{ dateISO, weight }`

**Служебные:**
- `pong` - ответ на ping для heartbeat
