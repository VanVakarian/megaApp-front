### 🚀 Real-time Sync (WebSocket): Концепт и План Внедрения [Frontend]

#### Цель
Интегрировать в Angular-приложение WebSocket-клиент, который будет устанавливать соединение с сервером, слушать события об изменениях данных и инициировать обновление локального состояния (`Signals`), чтобы UI автоматически и мгновенно отражал изменения, сделанные на других устройствах.

#### Концепция и Архитектура
Система будет построена на четком разделении ответственности между сервисами, что соответствует вашему текущему стилю.

1.  **`NetworkService` (Менеджер Соединения)**
    *   Единственный сервис, который "знает" о существовании WebSocket. Он инкапсулирует всю низкоуровневую логику.
    *   Будет использовать `rxjs/webSocket` для создания надежного и управляемого соединения.
    *   Реализует методы `connect()` и `disconnect()`. Метод `connect` также будет отправлять авторизационное сообщение с токеном.
    *   Реализует логику автоматического переподключения в случае обрыва связи.
    *   Предоставляет единый `Observable` (`getMessages()`) для всех входящих сообщений с сервера.

2.  **`AuthService` (Управляющий Жизненным Циклом)**
    *   Отвечает за то, *когда* нужно устанавливать и разрывать соединение.
    *   Вызывает `networkService.connect()` после успешного логина пользователя и при проверке аутентификации (`checkAuth`).
    *   Вызывает `networkService.disconnect()` при выходе пользователя из системы (`logout`).

3.  **Доменные Сервисы (`FoodDiaryService`, `FoodCatalogueService` и т.д.)**
    *   Являются "потребителями" данных.
    *   Подписываются на `Observable` сообщений из `NetworkService`.
    *   Фильтруют сообщения по `type`, чтобы реагировать только на те, что относятся к их домену (например, `DIARY_ENTRY_UPDATED`).
    *   **Ключевой момент:** Получив уведомление, сервис **не будет пытаться вручную изменить локальное состояние**. Вместо этого он вызовет свой собственный метод для запроса актуальных данных с сервера (например, `getFoodDiaryFullUpdateRange`). Это гарантирует консистентность данных и повторно использует уже существующую и протестированную логику.

#### План Внедрения

### ЭТАП 1: Настройка WebSocket-клиента

#### Шаг 1.1: Модернизация `NetworkService`
- Полностью заменить код в `src/app/services/network.service.ts` на реализацию с `rxjs/webSocket`.
- Реализовать методы `connect`, `disconnect` и `getMessages`. В `connect` добавить отправку `auth` сообщения с JWT-токеном.
- Добавить оператор `retry` в `pipe` для автоматического переподключения.

#### Шаг 1.2: Интеграция с `AuthService`
- Внедрить `NetworkService` в `AuthService`.
- В методах `login()` и `checkAuth()` после успешного подтверждения аутентификации добавить вызов `this.networkService.connect()`.
- В методе `logout()` добавить вызов `this.networkService.disconnect()`.

### ЭТАП 2: Реакция на серверные события

#### Шаг 2.1: Подписка на обновления в `FoodDiaryService`
- Внедрить `NetworkService` в `FoodDiaryService`.
- Создать приватный метод `subscribeToRealtimeUpdates()`, который будет вызываться в конструкторе.
- В этом методе подписаться на `networkService.getMessages()`, отфильтровав события по типам (`DIARY_ENTRY_CREATED`, `DIARY_ENTRY_UPDATED`, `DIARY_ENTRY_DELETED`).

#### Шаг 2.2: Реализация логики обновления
- Внутри подписки, при получении сообщения, извлечь из `payload` затронутую дату (`dateISO`).
- Вызвать существующий метод `this.getFoodDiaryFullUpdateRange(dateISO, 0)`, чтобы перезапросить данные только для измененного дня.
- Вызвать `this.foodStatsService.getStats()` для обновления статистики.

#### Шаг 2.3 (Аналогично): Подписка на обновления в `FoodCatalogueService`
- Внедрить `NetworkService` в `FoodCatalogueService`.
- Создать подписку на события, связанные с каталогом (например, `CATALOGUE_ENTRY_UPDATED`).
- При получении уведомления вызывать методы `getCatalogueEntries()` и `getCatalogueEntriesSelected()` для обновления всего каталога.

#### РЕЗУЛЬТАТ
- Приложение устанавливает WebSocket-соединение после входа пользователя.
- Соединение автоматически восстанавливается при обрывах.
- `FoodDiaryService` и другие доменные сервисы получают уведомления об изменениях.
- При получении уведомления данные на клиенте обновляются, и UI реактивно перерисовывается, отражая изменения с другого устройства.
- Архитектура легко расширяема для поддержки обновлений в других частях приложения (финансы, настройки).
